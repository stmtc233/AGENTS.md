# 性能

适用：启动慢、操作卡顿、吞吐不足，内存、磁盘、网络或电量占用过高，包体过大。

没有具体症状或目标时，不提前做性能优化。

## 先测量

- 写清现象、触发条件和要改善的指标。指标以用户感受为准，比如「从点击到列表显示」。
- 记录输入规模、运行环境和配置，保证前后可以对比。
- 先找到瓶颈（计算、I/O、网络、锁等待、内存），再决定怎么改。
- 先排除正确性问题：无休止的重试、没释放的资源、重复执行。不要用缓存掩盖 bug。

## 对比

- 前后使用相同的输入和环境，区分冷启动、预热后和缓存命中。
- 多次测量，看分布和尾部（P95、P99、最大值），不只看平均值。
- 一次只改一个主要因素，收益才能归因。
- 同时检查正确性和其他资源指标，不要为了一个数字恶化另一个。
- 写清计时的起点和终点。局部耗时不能说成端到端延迟。
- 模拟器和开发机上的数字不代表生产环境。

## 常见改进

- 渲染、事件回调和其他高频路径里，不做同步的磁盘或网络操作。
- 去掉循环里的重复查询、重复解析和全量扫描。
- 高频事件触发的刷新先合并再执行，比如 300 毫秒内最多刷新一次。
- 只读取需要的部分，不为一小段信息加载整个文件或数据集。
- 加缓存前确认结果确实可以复用，并定好失效条件和容量上限。
- 启动时只初始化必需的部分，其余推迟到第一次使用时。

## 并发与资源

- 并行度根据瓶颈设定，任务越多不一定越快。独占资源需要串行访问。
- 队列要有长度上限和满载时的处理策略。
- 后台任务和前台操作争抢资源时，按优先级限速或暂停后台任务。
- 任务取消后要真正停止工作并释放资源。

## 收尾

- 用原问题的指标报告效果，说明代价和剩余的限制。
- 留下能复现结论的命令或脚本，不要只给一个无法核对的百分比。
- 收益抵不上增加的复杂度时，撤回优化。
