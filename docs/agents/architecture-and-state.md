# 架构与状态

适用：调整模块边界、共享业务规则、状态管理、异步任务，或资源的创建与释放。

小范围修改沿用现有结构。出现真实的重复、耦合或并发问题时再加抽象。

## 边界

- 改之前弄清这段代码的输入、输出、拥有的数据、副作用和调用方。同类入口一起改，不要只修一处。
- 同一条业务规则只在一处实现，界面、接口、命令行、定时任务、远程端和 AI 工具都调用它。条件不满足就直接拒绝，不要偷偷排队或自动重试。
- 纯计算和决策逻辑（按钮是否可用、排序、分页合并）与 I/O（网络、存储、设备、界面）分开，规则才能单独测试。
- 界面层不直接调用网络或存储客户端。写操作走统一的控制层，错误码在一处转成用户能看懂的提示。
- 单个文件过长（参考值 400 行）或承担多个职责时，按功能拆分。项目有自己的上限就按项目的来。
- 共享资源（连接、文件句柄、设备）只由一个地方负责打开和关闭，其他模块通过接口使用。
- 不为想象中的需求搭通用框架。
- 新的实现要遵守原接口在完成、失败和取消时的约定，不只是返回值形状一致。

## 状态

- 身份、权限、连接状态和业务状态分开建模，改一个不应顺带改动另一个。
- 新增枚举值或状态时，找出所有穷举分支（`switch`、`when`、`match`）一起补齐。
- 业务判断读取真实数据，界面状态从数据推导，不能反过来。
- 「已发送」「已受理」「已开始」「已完成」是不同阶段，只报告有证据的那一个。
- 估算值、推测值和实测值分开保存，或标明来源。

## 异步任务

- 可能重叠的任务，给每次操作一个标识。回调先核对标识，过期的结果不能覆盖新任务。
- 任务使用开始时保存的参数快照，不在结束时读取可能已经变化的全局配置。
- 后台结果写回时，基于最新数据只更新自己负责的字段，不用旧对象整体覆盖用户后来的修改。
- 每个等待外部结果的流程都要有成功、失败、超时、取消四个出口，并走同一条清理路径：撤销定时器、订阅和监听。超时的含义见 [接口与事件](api-and-events.md)。
- 检查和执行之间条件可能变化时，用锁、版本号或原子操作保护。持锁期间不做网络请求或耗时计算。
- 有先后依赖的事件按顺序处理，无关的工作可以并行。不要为每条入站消息单独启动一个异步任务，后到的消息可能先执行。
- 上报、统计、日志、预览等旁路功能失败时只做记录，不能阻塞或延迟主流程。

## 生命周期

- 任务跟随真正拥有它的对象。离开页面、窗口重建、用户取消时是否停止，事先定好。
- 释放后重新获取独占资源时，等上一次释放完成再获取。
- 可能中途中断的长操作，记录足以识别半成品的状态，重启后能决定继续、回滚还是清理。

## 验证重点

- 验证状态和可观察的结果，不只断言某个函数被调用过。
- 异步改动重点测：重复触发、迟到的回调、乱序、取消与完成同时发生、连续两次操作。
- 生命周期改动测：离开再返回、重建，以及失败后能否再次使用。
