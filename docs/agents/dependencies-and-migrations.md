# 依赖与迁移

适用：新增、升级或移除依赖，更换框架、构建工具或公共接口。

## 先看清现状

- 依赖声明、锁文件、实际解析出的版本、代码里真正用到的 API，四者都要看。只看声明版本不能证明迁移已经完成。
- 沿用项目管理版本的方式（如统一的版本目录），同一个依赖不要在多处声明。
- 先跑一遍相关检查，记下已有的失败，以便区分哪些是迁移引入的。

## 新增依赖

- 先确认现有代码和已有依赖做不到。只为几行代码引入新依赖时，要说明理由。
- 核对维护状态、许可证、体积、所需权限、联网和自动初始化行为。
- 区分开发、测试和生产依赖，只引入需要的模块。
- 用项目的包管理工具更新清单和锁文件，检查有没有夹带无关的升级。
- 项目有开源许可声明页时，依赖增删同步更新。

## 升级与迁移

- 目标版本按需求来定。「升到最新」不是默认目标。
- 阅读目标版本的官方迁移指南和破坏性变更，列出本项目受影响的地方。
- 按行为核对替代 API：名字相近，不代表返回值、错误处理、线程和时序都相同。
- 优先使用公开、受支持的接口。使用内部 API 或反射读取私有字段要有理由、有对应的测试，并在代码旁注明升级该依赖时需要复核。
- 过渡用的兼容层写明职责和移除条件。
- 渐进迁移用棘轮守住：检查脚本禁止新增旧用法，存量记在基线文件里，基线只减不增。迁完一处就从基线删掉；不能靠往基线里加条目让检查通过。
- 留意间接用法：代码生成、编译插件、反射和序列化，不一定出现在普通的调用链里。
- 协议、公共 API 和持久化数据的兼容要求分别确认，见 [接口与事件](api-and-events.md) 和 [数据与文件](data-and-files.md)。

## 验证

- 构建工具变化：检查配置能被正确解析，产物正确。
- 运行时行为变化：实际运行受影响的功能。
- 有多个构建变体或平台时，覆盖受影响的那些，不只测默认的开发配置。
- 怀疑缓存掩盖了问题时，做一次干净构建。

## 收尾

- 删除旧代码、资源或配置前，在源码、构建脚本和外部接口里搜索引用。
- 删掉没人用的临时开关和迁移辅助代码。已经执行过的数据库迁移，以及仍需读取旧格式的代码要保留。
- 检查锁文件和生成物的变化，每一处都要说得出原因。
- 同步更新环境要求、命令和相关文档。
