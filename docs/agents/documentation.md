# 文档维护与演进

适用：修改 `AGENTS.md`、专题、`PROJECT_CONTEXT.md` 或接口说明；把这次任务的经验写进文档；新建专题；定期整理文档；升级通用规范。交接文档的写法见 [工作流程](workflow.md)。

这套文档是起点，不是终点。项目做得越久，文档里属于本项目的内容应该越多：术语、约束、踩过的坑、各模块的细则。每次任务都可能让它长一点，也可能让它删掉一些过期的东西。

## 文档的分层

| 层 | 文件 | 内容 | 什么时候读 |
|---|---|---|---|
| 核心 | `AGENTS.md` | 每次任务都要遵守的原则，按任务类型的路由表 | 每次 |
| 项目事实 | `PROJECT_CONTEXT.md` | 术语、目录、命令、约定、关键约束（每条一句）、按代码位置的改动路由、经验 | 每次 |
| 专题 | `docs/agents/*.md` | 某个主题的完整规则：做法、原因、后果、示例、验证 | 任务涉及时，动手前读完 |
| 模块 | 子目录的 `AGENTS.md` | 只属于这个目录的入口和约定 | 改这个目录时 |
| 代码注释 | 源码 | 某段代码为什么这样写 | 读代码时 |

专题有两种：随规范提供的通用专题（工作流程、测试、界面等），以及项目自己新建的专题（比如「支付流程」「同步协议」「设计系统」）。两种放在同一个目录，写法相同。

- 每次都读的两个文件只放摘要：关键约束每条一句，完整的原因和后果写进专题并链接过去。一句话摘要不足以安全改动，改相关代码前要读完专题。
- `AGENTS.md` 和 `PROJECT_CONTEXT.md` 合计尽量控制在 300 行以内。超出时，把细节移进专题。
- 同一条规则只在一个地方写全，其他地方一句话加链接。工具入口文件（如 `CLAUDE.md`）只做引用，不复制正文。

## 什么时候必须更新文档

以下情况，在同一次改动里更新，不留到以后：

1. 增删或重命名目录、模块、重要文件、构建配置：更新 `PROJECT_CONTEXT.md` 的「目录与模块」「常用命令」。
2. 新增或改变术语、角色、状态：更新「术语」，代码、界面和文档用同一个词。
3. 改接口、消息或数据格式：更新契约文档、所有调用方和相关专题。
4. 新增、修改或废弃一条约束：在专题里写全，在「关键约束」里加、改或删对应的一句话摘要。
5. 出现一个新主题：新建专题并登记路由，步骤见下文。
6. 改动发生在有自己 `AGENTS.md` 的子目录里：更新那一份。
7. 查明了 bug 的根因，或用户纠正了某个做法：按下面的「沉淀经验」处理。

同步了哪些文档，写在提交信息正文的最后一条，格式见 [文案与表达](copywriting.md)。

## 沉淀经验

经验按下面的路径逐级升级，每一级都在同一次改动里完成：

1. **记一条经验**。第一次遇到的坑、环境限制、用户的纠正，写进 `PROJECT_CONTEXT.md` 的「已知问题与经验」。一句话：现象加正确做法。
2. **升级为约束**。同类问题第二次出现，或者已经确认是长期规则，就把它改写成「关键约束」：做法加后果。用户定的产品取舍标「用户要求」。原来那条经验删掉。
3. **展开成专题**。一条约束需要解释原因、流程或示例才能讲清，或者同一主题的约束积累到三条以上，就把完整内容写进专题：属于已有专题的，写进该专题末尾的「本项目补充」；属于项目自己的业务或模块的，新建专题。「关键约束」里只留一句摘要加链接。
4. **删掉**。约束的原因不再成立（需求变了，或找到了更好的做法），直接改设计，并删除或改写这条约束，不在旁边留下旧说法。

不需要升级的内容：只影响这一次任务的细节、聊天过程、代码里一眼能看出来的事。

## 新建专题

1. 在 `docs/agents/` 下新建文件，用小写英文短横线命名，比如 `payment-flow.md`。
2. 按下面的骨架写，用不上的小节删掉。
3. 登记路由：按代码位置触发的，登记到 `PROJECT_CONTEXT.md` 的「改动路由」；按任务类型触发的（比如「发布到应用商店」），登记到 `AGENTS.md` 的路由表。至少登记一处，否则没人会读到它。
4. 关键的规则在「关键约束」里留一句摘要加链接。

```markdown
# 主题名

适用：改到哪些目录、模块或功能时读本文件。

一两句说明为什么需要这份专题：这里容易出什么错，出错的代价是什么。

## 子主题

- 做法。不这样做会怎样。
- 用户要求：产品取舍，AI 不能自行推翻。

## 示例

改前和改后，或者一个正确用法的最小例子。

## 验证

- 改完这部分要做哪些检查。

## 相关

- 相关专题或契约文档的链接。
```

单个专题超过约 300 行，或者混进了几个互不相关的子主题时，按子主题拆分，并同步路由。

## 写法

- 约束等于做法加后果。只在错误做法看起来很自然时才写「不要 X」，并写明 X 会导致什么。写不出后果的约束，删掉。
- 产品取舍标「用户要求」，和技术约束分开。前者不能自行推翻，后者在原因失效时直接改。
- 只写现状：按「现在的设计本来就是这样」来写。不出现「原先」「以前」「旧版」「曾经」「不再」「改为」，不写日期、版本沿革和复核记录。已删除的代码、接口和设置不留痕迹，改动经过只写进提交信息。仍需支持的旧数据格式、旧平台属于当前约定，照常写明。
- 用短句和祈使句，一条只说一件事。代码注释同样遵守：解释为什么，不复述代码，不写演变过程。
- 命令写明工作目录，没跑过的标「未验证」。路径用仓库内的相对路径，不写个人电脑上的绝对路径或临时目录。
- 不确定的写「待确认」，不为了填满表格编造内容。涉及版本行为或平台限制的结论，注明适用版本或来源。
- 「保证质量」「遵循最佳实践」这类无法执行的话不要写。

新增一条规则前，逐项检查：

1. 它会影响正确性或协作，而不是人人都知道的常识。
2. 写清了适用条件、怎么做，以及不这样做会出什么问题。
3. 没有意思相近的已有规则。有的话，修改原来那条。
4. 放对了层：只属于本项目的，不写进通用专题的正文。
5. 如果来自第三方资料，用自己的话归纳。需要引用原文时，先确认许可。

## 文档和代码不一致

先告诉用户哪里不一致。能从证据判断是代码有 bug 还是文档过期的，直接修正并说明；会改变产品承诺或安全边界的，等用户决定。不要默默按其中一边改。

## 定期体检

文档会随时间老化。用户要求整理文档，或者发现文档明显和代码对不上时，做一次体检：

- 对照代码核实命令、路径、术语和模块划分是否仍然成立。
- 删除失效的规则，合并意思重复的规则。
- 「已知问题与经验」里反复出现的升级为约束，已经不存在的问题删掉。
- 每次都读的文件超出篇幅时，把细节移进专题；过长的专题按子主题拆分。
- 检查每个专题都能从路由表找到，链接都有效。

体检只改文档。发现代码问题时，列出来交给用户决定。

## 升级通用规范

本规范发布新版本后，按以下方式合并进项目：

- 通用专题按条目对比新旧版本，合入新增和修改的条目。每个专题末尾的「本项目补充」、`PROJECT_CONTEXT.md` 和项目自己的专题保持不动。
- 项目改过的通用条目，保留项目的版本，并在汇报里列出，由用户决定是否采用新版。
- 新版删除的条目，先确认项目是否还依赖它，再决定删不删。
- 合并后检查路由表和链接。

反过来，项目里验证过、去掉项目细节后仍然成立的规则，可以提交回通用规范，让其他项目也用上。

## 改完检查

链接和路径有效，路由表与实际文件一致，规则之间不矛盾，没有残留的占位符或敏感信息。
