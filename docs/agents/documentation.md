# 文档维护

适用：修改 `AGENTS.md`、专题细则、`PROJECT_CONTEXT.md` 或接口说明。交接文档的写法见 [工作流程](workflow.md)。

## 写在哪里

| 内容 | 位置 |
|---|---|
| 每次任务都要遵守的原则 | 根目录 `AGENTS.md` |
| 按主题划分的通用细则 | `docs/agents/` |
| 本项目的事实、命令、约定、踩过的坑 | `PROJECT_CONTEXT.md` |
| 某个模块自己的入口和约定 | 该目录下的 `AGENTS.md` |
| 某段代码为什么这样写 | 代码注释 |

- 同一条规则只写在一处，其他地方链接过去。工具入口文件（如 `CLAUDE.md`）只做引用，不复制正文。
- 通用文件尽量不改，项目特有的内容写进 `PROJECT_CONTEXT.md`。以后更新通用文件时就不会冲突。

## 让文档跟上项目

- 结构、公共接口、数据格式、权限或长期约定变化时，在同一次改动里更新文档。
- 用户纠正了某个做法，或者同一个问题第二次出现，就把结论写进 `PROJECT_CONTEXT.md` 的「已知问题与经验」。一句话写清现象和正确做法。
- 规则失效就修改或删除，不要在旁边追加互相矛盾的例外。
- 只写当前有效的内容，历史和废弃的方案留在提交记录里。仍需支持的旧数据格式和旧平台属于当前约定，要保留。
- 文档和代码对不上时，先判断是代码有 bug、文档过期，还是需求尚未确认。会改变产品承诺或安全边界的，问用户。

## 什么值得写成规则

新增一条规则前，逐项检查：

1. 它会影响正确性或协作，而不是人人都知道的常识。
2. 写清了适用条件、怎么做，以及不这样做会出什么问题。
3. 去掉具体的项目名、类名和路径后仍然成立。否则放进 `PROJECT_CONTEXT.md`。
4. 没有意思相近的已有规则。有的话，修改原来那条。
5. 如果来自第三方资料，用自己的话归纳。需要引用原文时，先确认许可。

「保证质量」「遵循最佳实践」这类无法执行的话不要写。

## 写法

- 用短句和祈使句，一条只说一件事。
- 命令写明工作目录，没跑过的标「未验证」。
- 路径用仓库内的相对路径，不写个人电脑上的绝对路径或临时目录。
- 不确定的写「待确认」，不为了填满表格编造内容。
- 涉及版本行为或平台限制的结论，注明适用版本或来源。

## 改完检查

链接和路径有效，路由表与实际文件一致，规则之间不矛盾，没有残留的占位符或敏感信息。
