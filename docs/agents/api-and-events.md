# 接口与事件

适用：修改 HTTP/RPC 接口、消息格式、事件订阅、Webhook、第三方回调或提供给 AI 的工具接口。

## 契约

- 先找到契约的权威定义（schema、类型定义或接口文档）以及所有生产方和消费方，改动时一起更新。
- 契约写清：类型、单位、时区、能否为空、默认值、枚举取值、错误码和所需权限。
- 区分「字段省略」「显式 null」「空集合」和「零」。部分更新和整体替换分开定义，防止误清数据。
- 金额、时间、计数写明精度和取整位置。展示格式不能当作存储格式。
- 多端共享的规则通过共享定义、代码生成或契约测试保持一致。

## 兼容

- 先确认项目的发布方式：各端同时升级，还是独立发布、需要兼容旧版本。策略记在 `PROJECT_CONTEXT.md`。
- 字段含义、编码或时序的变化都要评估兼容性，新增可选字段也可能影响消费方。
- 不兼容时尽早返回可识别的错误，不让对方带着误解继续执行。
- 没有实际消费方的兼容代码不要保留。

## 写操作

- 查询和修改分开。接口名称和说明要让调用方看出有没有副作用。
- 权限和状态在服务端校验，所有入口共用一套，见 [安全与隐私](security-and-privacy.md)。
- 可能重复提交的写请求要幂等：优先用资源 ID 或条件更新；使用幂等键时，同一个键带着不同内容应拒绝。
- 超时不等于失败，只说明结果未知。重试前先查询状态，或依靠幂等保证不会重复执行。
- 多步的读取、校验和写入用事务或条件更新保护，不能只在打开页面时检查一次。
- 批量删除、覆盖等高影响操作先给出预览：范围、影响和不可恢复的部分。执行时重新校验，数据已经变化就重新预览。

## 外部系统

- 数据库事务管不到外部服务。支付、通知、创建外部资源等操作，先持久化操作意图，再用固定的幂等键调用，最后记录结果，以便重试和对账。
- 调用外部服务期间不要持有数据库锁。
- 调用前核对环境、账号和目标对象。

## 事件与长连接

- 说清事件是完整状态、增量，还是「请重新拉取」的通知，以及会不会重复、乱序或丢失。
- 状态提交成功后再发事件。需要可靠送达的业务不能只靠内存广播。
- 消费方按实体 ID 或版本号处理事件，发现版本缺口时重新拉取完整数据。
- 慢消费者要有缓冲上限。允许丢弃时，必须留有重新同步的途径。
- 断线重连使用有上限的退避，认证失效和网络中断分开处理。
- 权限撤销后，已经建立的连接也要按设计失效。

## 验证重点

按改动选择：正常请求、权限不足、重复提交、并发修改、超时后恢复、断线重连。每个受影响的消费方都要覆盖。
