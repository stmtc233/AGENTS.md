# 文案与表达

适用：界面文字、错误提示、通知、文档、代码注释、提交信息，以及给用户的回复。

AI 写文案时，习惯把自己的推理过程原样搬进去：实现条件、因果链、适用范围、好处和撤销方法挤在一句话里。提交信息也一样，整份说明塞进标题行。读者通常只花几秒，要给的是结论，不是推导。

## 界面文案

### 默认不写

要在界面上加一行字（副标题、提示、说明、状态行）之前，先问：删掉它，用户还能操作、还能看懂状态吗？能就不写。交互和状态尽量由控件本身表达。

### 写什么

- 只写用户要知道的结果和下一步：会怎样，该做什么。为什么会这样是实现细节，不写进文案。
- 不写条件分支。「A 不行就用 B，B 不行再用 C」只留用户当下面对的那个结果；不需要用户操作的自动回退不写。
- 不复述。副标题不重复标题；下方控件已经显示的值不再写一遍；没有标题之外的新信息，就不写副标题。
- 只用界面上的名字。提到按钮、页面、设置项时用原名加「」；同一个操作在所有端只有一个叫法。代码里的概念名不进文案。
- 不用口语词（「就」「一下」「其实」「哦」「啦」「~」），不写逗号长链，一句只说一件事。按钮用动词短语，比如「保存草稿」，而不是「确定」。
- 好处只在它是用户决定开关的依据时才写，并压缩到几个字，比如「省电省流量」。

### 错误与状态

- 先说后果，再说用户能做什么。不道歉，不解释内部原因；需要排查时，原因码放在括号里。
- 校验不通过、网络问题、没有权限、结果未知是不同的情况，不要都写成「操作失败」。
- 没有确认结果时，不写「已保存」「已发送」。处理中、等待确认和已完成要用不同的说法。
- 危险操作写清对象、范围和能否恢复，按钮写具体动作，比如「删除 3 个文件」。
- 重要的失败和需要用户处理的提示，不能只用几秒后就消失的通知。

### 标点

- 中文文案用全角标点（，。；：？！（）），引号和按钮名用「」。全角标点前后不加空格。
- 以下内容保留半角：数字和时间（`1,000`、`1:05.67`）、网址和地址、快捷键、正则、CSV 等数据格式示例，以及日志、异常消息和写给 AI 读的工具说明。

### 长度

中文界面的参考上限如下，按汉字计，变量取典型值。项目可以在 `PROJECT_CONTEXT.md` 里调整。

| 位置 | 上限 |
|---|---|
| 标题、按钮、开关名、分段选项 | 12 字 |
| 列表行或开关的副标题 | 一行，20 字 |
| 对话框正文 | 2 句、60 字；风险确认最多 3 句，并列的多项事实分行写 |
| 状态条、提示条、Toast | 15 字 |

超出上限时，先删实现细节和重复信息。删完还放不下，说明这段内容应该放进帮助页或教程，而不是塞进副标题或弹窗。

### 示例

开关「空闲时暂停同步」的副标题，开关下方有时长选择：

```
改前：设备连续 $minutes 分钟没有操作，就在两次同步之间暂停后台同步，省电省流量；首页点「立即同步」恢复
改后：省电省流量，上传中不会暂停
```

改前复述了标题和下方的时长，还写了实现时机、适用范围和恢复方法。「立即同步」按钮本来就在首页，不用提前教。

登录过期的提示：

```
改前：由于访问令牌已过期且刷新请求返回 401，系统尝试使用本地缓存凭据重新认证也失败了，您需要重新登录，建议检查网络连接后重试。
改后：登录已过期，请重新登录。
```

改前把整条判定过程和内部原因都写了出来。用户改变不了令牌的状态，只需要知道结果和下一步。

## 去掉 AI 味

以下写法一看就像机器生成，在文案、文档、注释和回复里出现时，删掉或改写：

- 空洞的形容词和营销词：无缝、赋能、一站式、极致、全方位、强大、轻松。
- 套路句式：「不仅……更……」「在当今……的时代」「让……变得更简单」「我们致力于……」。
- 为了凑节奏的三段排比和对仗。
- 套话开头和结尾：「首先」「值得注意的是」「总而言之」「希望对你有帮助」。
- 到处加粗，每段配 emoji，句末用感叹号。
- 一句话能说清的事，拆成小标题加列表。
- 翻译腔：「进行了一个优化」「基于……的考虑」「对……进行处理」。
- 文档和注释里讲演变过程（「原先」「改为」「现已」），规则见 [文档维护与演进](documentation.md) 的「写法」。
- 注释复述代码在做什么（`// 遍历列表`），而不是解释为什么这样做。

改写的方法是换成具体事实：「大幅提升性能」改成「列表加载从 3 秒降到 0.5 秒」，「操作失败」改成「网络已断开，修改未保存」。

## 提交信息

项目有约定就按约定写。没有约定时，用下面的格式：

```
type(scope): 摘要

- 正文每条一句
- ……
- 同步更新 xxx.md
```

- 标题：`type` 取 `feat`、`fix`、`refactor`、`perf`、`docs`、`test`、`build`、`chore`，`scope` 取模块名。摘要不超过 30 字，写用户能看到的变化或修掉的现象，不写实现手段、类名和常量值，末尾不加句号。一个标题装不下两件事，就拆成两个提交。
- 正文：空一行后写 3 到 8 条，只写差异里看不出来的内容：为什么这样做、关键取舍和边界、已知限制、验证情况（在什么环境验证的，没验证就写没验证）。
- 不复述差异，不罗列改了哪些文件、函数和常量。只有读者必须知道的入口（新的公共接口、数据迁移）才点名。
- 修 bug 写一条「原因：……」，不写「原先……后来发现……」式的经过。
- 同步了文档就写在正文最后一条：「同步更新 xxx.md」。
- 多行内容用 heredoc 交给 `git commit -F -`，不要全部塞进一个 `-m`。

示例：

```
改前（只有一行标题，写了全部内容）：
feat(sync): 新增空闲时暂停同步(默认关):设置→同步新增开关与时长(1/3/5 分钟，默认 3)，连续 N 分钟无操作判定为空闲，因为暂停需要重建连接，所以只在两次同步之间……

改后：
feat(sync): 空闲时暂停后台同步

- 设置 → 同步新增开关与时长（1 / 3 / 5 分钟，默认 3），默认关
- 只在两次同步之间暂停，上传中不暂停，避免文件传到一半中断
- 补单测；Pixel 8 真机验证暂停与恢复
- 同步更新 PROJECT_CONTEXT.md
```

```
fix(list): 快速连续刷新时列表显示旧数据

- 原因：后发出的请求先返回，随后被先发出的请求结果覆盖
- 每次刷新带请求序号，只采用最新一次的结果
- 补单测覆盖乱序返回；未在真机验证
```

## 回复用户

- 先给结论，再给支撑结论的证据，不按操作顺序复述过程。
- 「计划做」「推测」「已验证」「已完成」分开说。
- 需要用户决定时，给出具体的问题、选项、影响和你的建议。
- 不寒暄，不复述用户的问题，结尾不做没有新信息的总结。
- 不提自己是按哪份文档或什么格式写的，直接给内容。
