# 文案与表达

适用：界面文字、错误提示、通知、文档、代码注释、提交信息，以及给用户的回复。

## 基本原则

- 先判断是否需要这段文字。控件和标题已经说清楚的，不再加解释。
- 写用户此刻需要知道的事：发生了什么，有什么影响，下一步做什么。
- 一句话说一件事。按钮用动词短语，比如「保存草稿」，而不是「确定」。
- 同一个概念在所有地方用同一个词。提到按钮或设置项时，用界面上的原名。
- 数字、单位、日期和标点遵循项目的语言习惯。命令、路径和需要复制的内容保持原样。

## 去掉 AI 味

下面这些写法一看就像机器生成，出现时删掉或改写：

- 空洞的形容词和营销词：无缝、赋能、一站式、极致、全方位、强大、轻松。
- 套路句式：「不仅……更……」「在当今……的时代」「让……变得更简单」「我们致力于……」。
- 为了凑节奏的三段排比和对仗。
- 套话开头和结尾：「首先」「值得注意的是」「总而言之」「希望对你有帮助」。
- 到处加粗，每段配 emoji，句末用感叹号。
- 一句话能说清的事，拆成小标题加列表。
- 翻译腔：「进行了一个优化」「基于……的考虑」「对……进行处理」。
- 注释复述代码在做什么（`// 遍历列表`），而不是解释为什么这样做。

改写方法是换成具体事实：「大幅提升性能」改成「列表加载从 3 秒降到 0.5 秒」；「操作失败」改成「网络已断开，修改未保存」。

## 错误与状态提示

- 先说影响，再说怎么办。技术细节放在日志或「详情」里，不直接显示堆栈。
- 校验不通过、网络问题、没有权限、结果未知是不同的情况，不要都写成「操作失败」。
- 没有确认结果时，不写「已保存」「已发送」。处理中、等待确认和已完成要用不同的说法。
- 危险操作写清对象、范围和能否恢复，按钮写具体动作，比如「删除 3 个文件」。
- 重要的失败和需要用户处理的提示，不能只用几秒后就消失的通知。

## 提交信息

- 按项目已有的格式写。没有约定时，标题用一句话说清改了什么；正文写差异里看不出的原因、影响和未验证的部分。
- 不罗列改过的文件和函数。一个提交说不清多件事时，考虑拆开。

## 回复用户

- 先给结论，再给支撑结论的证据，不按操作顺序复述过程。
- 「计划做」「推测」「已验证」「已完成」分开说。
- 需要用户决定时，给出具体的问题、选项、影响和你的建议。
- 不寒暄，不复述用户的问题，结尾不做没有新信息的总结。
