# 测试与验证

适用：实现、修复、重构、迁移，以及任何需要证明「已经完成」的任务。

## 先想清楚要证明什么

- 把需求写成可检查的结果：在什么条件下、做什么操作、应该看到什么。
- 修 bug 先复现。复现不了，就写明已知条件和尚未验证的假设。
- 沿用项目已有的测试框架和命令。
- 动手前先跑一遍相关检查，记下已有的失败，以便区分哪些是本次引入的。

## 选择范围

| 改动涉及 | 重点证明 |
|---|---|
| 逻辑、校验、状态转换 | 正常输入、边界值、错误路径 |
| 模块之间、接口、序列化 | 生产方和消费方实际能对上 |
| 存储、导入导出 | 数据完整，中断后能恢复，旧数据能读 |
| 界面 | 典型状态下的操作、布局、焦点和可访问性 |
| 平台、设备、外部服务 | 在目标环境中走通完整链路 |
| 性能 | 相同条件下的前后对比，见 [性能](performance.md) |

- 先跑最能暴露问题的检查，再根据影响面扩大范围。
- 只改文档或低风险样式时，人工核对即可，不必为了形式补测试。
- 修复关键缺陷时，留一个能区分修复前后行为的回归测试。

## 各层能证明什么

- 单元测试证明局部逻辑。模块能否正确协作靠集成测试，目标设备和生产环境上的表现要在那里实际运行。
- 改动影响用户流程时，从真实入口一直走到最终结果，只看底层调用成功不够。
- 涉及压缩、混淆、打包的改动，在发布构建上验证。
- 模型或启发式算法要用一组有代表性的样本验证，包括会失败的样本。一次演示成功不算数。

## 写稳定的测试

- 测行为，不测实现步骤，不要把实现逻辑抄进断言。
- 异步测试等待明确的条件并设置超时上限，尽量不用固定延时。
- 测试数据互相隔离，结束后释放占用的资源。
- 测试失败先找原因。偶发失败也要查清，不能靠重跑了事。
- 不为了让测试通过而放宽断言、跳过步骤或修改无关的预期值。

## 报告

- 结果分为通过、失败、未运行、不确定，各自说明原因。
- 写清实际测了哪一段、哪些环境没有覆盖。推断不能写成已验证。
- 日志和截图只保留必要的信息，去掉凭据和个人数据。
